# リファクタリング・ワークストリームの型

挙動保存の置換・形式変更を「賢さ」ではなく「装置」で守るための型。
2026-07 の headless-paint 中間層リファクタ + persistence-hardening で確立した。

固定の順序: **① 現状を機械的に固定 → ② 対応表で設計レビュー → ③ 実装（委譲） → ④ 検収ゲート**

## ① golden 先行（コードに手を入れる前）

- 現状の出力（シリアライズ形式・ディスクファイル・ピクセル）を fixture として repo に焼く
- 非決定要素は排除する: 時刻・ID は注入、圧縮バイト依存の値（sha256 等）はマスクか decode 後比較
- 決定性を確認する（同一入力で2回実行して一致）
- 障害系も「現状こうなる」を fixture 化する（弱点の記録。修正後に期待値を書き換えることが受け入れテストになる）
- 効果: 以後の全変更で「意図的変更」と「事故」を機械で区別できる。実績として、意図しないフォーマット変化と潜在バグの両方を検出した

## ② 対応表 = レビュー1回 = テスト仕様書

- 判断が割れる箇所（イベント×遷移、操作×永続化、割り込み×許可/禁止）は**全域を1枚の表**にする
- 表の形式: 各行 = 「イベント / 前提 / 変更するもの（それ以外は不変） / 結果」
- **表だけをユーザーレビューにかける**（設計全体を都度レビューしない。ユーザーの時間は判断が割れる箇所だけに使う）
- 承認された表の**各行を 1:1 でテスト化**する。表がそのままテスト仕様書になる
- 危険なシーケンス（並行・競合）は「必須検証シーケンス」として表に明記し、必ずテスト化する

## ③ 実装（委譲）

- delegation skill の型に従う（必読ファイル・変更禁止・停止条件・報告フォーマット）
- 大きな変更は「挙動保存の抽出」と「挙動変更」を別タスクに分ける（例: codec 抽出→gen 導入を別コミットに）
- 純粋コア + 薄い命令的シェルに寄せる。判定基準は「**各事実を知る場所が1箇所か**」

## ④ 検収ゲート（WS 完了ごと）

- build / フルユニット（browser mode 込み）/ lint / E2E すべて green
- golden 不変（意図的更新は1件ずつ理由をコミットメッセージに記録）
- 核心テスト（対応表の行・互換性・ロールバック）の現物確認（grep）
- 実ブラウザで実フローを駆動（破損・復元・排他などユニットで再現しにくいもの）
- green になってからコミット。1 WS = 追える粒度のコミット列

## 互換性の鉄則

- リリース済みデータ形式は「旧形式の読み取り互換」が絶対条件
- 旧形式のテストは「フィールドが無い」だけでなく「**ファイル・レコード自体が無い**」ケースまで含める
  （実例: 旧 doc には manifest 自体が無いものがあり、entry 欠落のみのフォールバックでは後方互換が壊れた）
- 新形式の読み手は未知フィールドを無視し、旧レコードの廃止フィールドも無視する（migration 不要の共存）

## 完了時

- plan md に結果を追記して**凍結**（以後書き換えない）
- ユーザー承認された確定判断は `docs/decisions/` へ昇格
- 上位ドキュメント（docs/）の虚偽チェック（実装が記述を虚偽にしていないか）
- planning-flow の完了時フローに従う
